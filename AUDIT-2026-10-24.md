# ScatterSteg security and correctness audit — 2026-10-24

Scope: the whole repository at `e6b3a63`: the C implementation (`main.c`, `embed.c`, `stc.c`, `prng.c`, `png_io.c`, `jpeg_io.c`, `atomic_write.c`), the Rust port (`rust/src/`), and the fuzz targets. Each claim in `THREAT_MODEL.md` was treated as something to try to break. No code was changed.

**Bottom line.** No memory-safety bug, crypto misuse or cheaper passphrase test was found. `make test` (unit and CLI tests under ASan and UBSan, plus fault injection) passes with no sanitizer reports. The findings are about the steganographic claim (A1), the swap-locking claim (A6) and resource bounds (A5), plus some stale docs.

## Confirmed findings

### 1. Medium: an RGB cover whose pixels are all gray is accepted, and the output is trivially detectable (A1)

**Status (2026-10-29): fixed** in `f25d450`, both builds: an RGB cover that is gray in every pixel, or whose sBIT says fewer than 8 bits, is refused. A cover that is gray in *nearly* every pixel is still accepted.

- **Where:** `png_io.c:136-143` (the `unsuitable` checks) and `rust/src/png_io.rs:219`.
- **Scenario:** a grayscale photo, scan or screenshot saved as 8-bit RGB, with R = G = B in every pixel. This is very common. `encode` accepts it and changes R, G and B independently.
- **Reproduced:** a 512×512 RGB PNG with R = G = B in every pixel, carrying a 27-byte message. The encode succeeds, and the output has **93 pixels where R, G and B are not all equal**; the cover had none. A one-line check ("does any pixel have R ≠ G?") flags the image with no false positives on true gray-in-RGB images. Every message sets some off, however small.
- **Related (suspicion, not reproduced):** an `sBIT` chunk with fewer than 8 significant bits is copied to the output (`kept_chunks`, `png_io.c:228`). Images that carry one usually have structured low bits (zeros, or the high bits repeated). ±1 changes break that structure, and the kept `sBIT` tells a warden to look. The same goes for any cover that was expanded from a lower bit depth.
- **Fix:** refuse (or at least warn about) RGB covers where R = G = B for all or nearly all pixels, and covers whose `sBIT` is below 8. More generally, refuse covers whose LSBs are visibly structured: for example, a channel whose LSB plane is constant, or exactly equal to another channel's.

### 2. Low–Medium: large secrets are not locked against swap, despite what A6 says

**Status (2026-10-29): mitigated** in `efece34`: the soft `RLIMIT_MEMLOCK` is raised to the hard limit at startup, encode and decode warn when the message or plaintext can't be locked, and `THREAT_MODEL.md` (A6) states the limit. `read_message` still doubles its buffer, briefly holding two copies.

- **Where:** `main.c:409` (plaintext), `main.c:574` (message buffer growth), `rust/src/sodium.rs:126` (`Secret::new`).
- **Scenario:** `sodium_malloc` ignores a failed `mlock`. With the default `RLIMIT_MEMLOCK` of 8 MiB, any secret buffer past the remaining locked budget is ordinary swappable memory. `read_message` also doubles its buffer, keeping two copies during each growth.
- **Reproduced:** under an 8192 KB limit, `sodium_malloc(64 MB)` succeeds and `VmLck` stays at 1028 kB. Messages or plaintexts of a few MiB or more can reach swap. Core dumps stay disabled; only swap is affected.
- **Fix:** after allocating, check `VmLck` or call `sodium_mlock` yourself and check its result. Warn or refuse when it fails, or raise the soft `RLIMIT_MEMLOCK` to the hard limit at startup. At minimum, state the limit in `THREAT_MODEL.md` (A6).

### 3. Low: a 5 KB JPEG costs ~16 s of CPU and ~1 GiB of RAM to load (A5 amplification)

**Status (2026-10-29): fixed for Huffman-coded files.** `331a3bb` caps the blocks all scans visit (the 5 KB file is refused in about a second). For the follow-up below, `27d8477` moved encode's size check before the rewrite check, and `5087c0b` refuses a Huffman frame declaring more blocks than its file has bits, before anything is allocated (the hollow file now takes ~1 ms). An arithmetic-coded hollow file can't be bounded that way and still costs ~0.35 s and ~1 GB before it is refused; `THREAT_MODEL.md` (A5) says so. The original fuzz input was lost; `tests/fuzz/regressions/jpeg_load/hollow-huge-frame.jpg` rebuilds it.

- **Where:** `jpeg_io.c:24` (`JPEG_MAX_SCANS 500`), `jpeg_io.c:60` (`silent` swallows warnings), `rust/src/jpeg_io.rs:33`.
- **Scenario:** a progressive JPEG with a 23000×23000 gray frame and 500 empty, repeated DC scans, 5,108 bytes in all. libjpeg treats a repeated scan (`JWRN_BOGUS_PROGRESSION`) and missing entropy data as warnings, so all 500 scans run over the whole frame.
- **Reproduced:** with a harness calling `jpeg_load` (`-O2`, libjpeg-turbo 3.2.0), it loads successfully in **16.4 s**, and allocates the full 512 MB of coefficients plus libjpeg's buffers. At 4096² the same file shape takes 0.5 s. `encode` loads the image twice (once more for `jpeg_check_writable`). The time is bounded, so the claim technically holds, but that's a lot of work for a 5 KB file to cause.
- **Fix:** treat `JWRN_BOGUS_PROGRESSION` (and possibly `JWRN_HIT_MARKER` repeated across scans) as fatal, using an `emit_message` hook that checks `msg_code`. Or cap the total work (scans × blocks) rather than the scan count alone, or lower the cap to ~100.

**Follow-up (2026-10-26, found by diff_jpeg):** the block cap doesn't cover a single baseline scan over a huge frame. A 178-byte gray JPEG declaring 15144×32800 (994 MB of coefficients, under the 1 GiB cap) with almost no entropy data takes 1.3 s to load and 2.25 s more for `jpeg_check_writable`, peaking at 1.9 GB of RSS, and yields 2 carriers. It makes `diff_jpeg` exceed its 60 s timeout (it loads, saves and reloads in both builds). **Partly fixed (2026-10-26, `refuse-small-jpeg-early`, merged into main):** encode now refuses a cover too small to hold a message before `jpeg_check_writable` (`codec_too_small`), so this file costs encode 1.2 s instead of 3.3 s (Rust 0.85 s instead of 2.4 s). Still open: the first load (1.3 s, ~1 GB) is paid by encode and decode alike; refusing a frame whose entropy data is implausibly short for its block count would remove it. Also: no CLI test now reaches the rewrite-check refusal (the three fuzz-found files are refused as too small first); unit tests in both builds cover it, and the output check catches a rewrite mismatch end to end. The input is `rust/fuzz/corpus/diff_jpeg/a482169c6ced8925f050763667153bb06729c501` (local corpus, untracked).

### 3b. Low: C and Rust treat an ancillary chunk with a bad CRC differently (found while fixing finding 1)

**Resolved (branch `keep-bad-crc-chunks`):** Rust now keeps such chunks, as libpng does. This had been a documented, deliberate difference in `rust/README.md`. While comparing written chunks, CI also found that C wrote back reserved-bit chunk names under older libpng, which newer libpng refuses; C now leaves them out, like Rust.

- **Where:** `png_io.c` (libpng with `PNG_HANDLE_CHUNK_ALWAYS`) vs `rust/src/png_io.rs` `parse_chunks`.
- **Reproduced:** a cover with a `tEXt` chunk whose CRC is bad. The C build's output contains that `tEXt` with a *corrected* CRC; the Rust build's output drops it. So the same cover gives outputs that differ, and the C output "repairs" damage the cover had, which a warden comparing against a known original could notice.
- **Fix:** pick one behavior. Dropping is what the PNG spec suggests for corrupt ancillary chunks; C would have to verify CRCs itself, because libpng keeps the chunk. The fix for finding 1 makes the `sBIT` check see a bad-CRC `sBIT` in both builds, so they agree on refusal either way.

## Suspicions and hardening (not reproduced, or not bugs as such)

### 4. Low: peak memory at decode is well above the documented 1 GiB caps

**Status (2026-10-29): documented, not reduced.** `e34bbe2` rewrites A5 to say the caps bound each allocation, not their sum, with the decode peak (about 3.5 GB for the largest RGB PNG) and encode's HILL cost map. Packing `y` and `m` would lower the decode peak.

- **Where:** `main.c:360-361` (`y`, `m` and `payload` in `read_payload_v3`), `rust/src/codec.rs:194` and following; the Rust JPEG loader also keeps the file bytes and a full copy of the coefficients (`rust/src/jpeg_io.rs:242`).
- **Scenario (computed):** a 2²⁸-pixel RGB PNG holds 805 MB of pixels and needs a 1 GiB permutation. With a wrong passphrase, the 32-bit length is random. When it fits, which happens for a few percent of guesses on a large image, `y` and `m` take one byte per bit: up to 805 MB each. That is about 3.5 GB in all. In Rust, a JPEG needs the file, libjpeg's arrays and a copy, about 2 GiB at decode and more at encode (`check_writable` decodes a second copy). Everything is bounded, but the numbers in the threat model read as the total.
- **Fix:** have `stc_extract` read carrier bits straight from the image instead of building `y`, and pack `m` into bytes as it goes. Document the real peak.

### 5. Low (hardening): encode never checks that its output decodes

**Status (2026-10-29): fixed** in `6288a32`, as described below.

**Resolved (branch `verify-output`):** encode now writes the output to memory, reads it back and compares a BLAKE2b digest of the carrier (every sample or carrier coefficient, in order) with the one it embedded, before anything touches disk. A mismatch fails the encode and leaves an existing output file as it was. The cover is freed before reading back, so peak memory doesn't double. The fault sweeps force the mismatch path, in both builds.

- **Where:** `main.c:866` and `rust/src/main.rs:375`.
- **Scenario:** `jpeg_check_writable` round-trips the *cover*, but nothing round-trips the *stego* output. Any future libjpeg or png behavior that changes a coefficient or sample on write would lose the message silently. The fuzzer has already found files where this happens to the cover.
- **Fix:** after saving, reload the output and check that the carrier LSBs, or at least the payload syndrome, match. This skips a second Argon2id because the keys are still in memory. It's cheap insurance.

### 6. Low: the secret embedding order is freed without being wiped

**Status (2026-10-29): fixed** in `b519bf7`: the order and the v1 keystream are wiped before freeing (`free_order`, `Zeroizing` in Rust), and this survived the move to `codec.c`.

- **Where:** `main.c:466, 487, 848` (`free(order)`), `prng.c:40` (the v1 keystream `stream`), and the Rust `Vec<u32>` orders.
- **Scenario:** the permutation is derived from the scatter key. Leaking it doesn't expose the message (that needs the encryption key), but it does tell a local attacker where the payload is, which A6 tries to prevent. Everything else secret is wiped.
- **Fix:** `sodium_memzero` it before freeing (`zeroize` in Rust).

### 7. Low (suspicion): the output's file structure fingerprints ScatterSteg, and tells the two builds apart

**Status (2026-10-29): open.** Neither build matches the cover's IDAT chunking or zlib settings, and the builds still write differently. `README.md` says the output isn't byte-identical to the cover, but nothing yet states that its structure can identify ScatterSteg.

- **Where:** `png_io.c` (`write_png`, libpng's defaults) and `rust/src/png_io.rs:366` (64 KiB IDAT chunks, its own filter choice).
- **Scenario:** a warden doesn't need steganalysis to find images re-encoded by ScatterSteg, only IDAT chunk sizes, zlib settings and filter patterns that differ from the camera's or editor's output. The C and Rust builds write differently from each other. For JPEG, the output has libjpeg's marker order and scan script. The README notes the file isn't byte-identical, but A1 says the output is "in the cover's own format and metadata."
- **Fix:** match the cover's IDAT chunk size, and make C and Rust write identical bytes, or document this as a known tell.

### 8. Passphrases are silently cut at the first NUL

**Status (2026-10-29): fixed** in `b519bf7`: encode refuses a passphrase containing a NUL. Decode still cuts at the first NUL, so images made with such a passphrase before the fix still open.

- **Where:** `main.c` (`strlen`) and `rust/src/main.rs:142` (on purpose, for compatibility).
- **Scenario:** a pasted passphrase containing a NUL byte becomes only the part before it. Encode's 12-byte minimum is checked on the truncated value, so it can't drop below 12 bytes, but a strong passphrase can silently become a weaker one.
- **Fix:** refuse a passphrase containing a NUL instead.

## Gaps in fuzz and test coverage

**Status (2026-10-29):** the first two are closed (`2aaba26`). Time and memory per input are still untested; finding 3's follow-up was found by `diff_jpeg` timing out, not by a check for it.

**Resolved (branch `fuzz-decode`), the first two:** the file format moved from `main.c` to `codec.c`, so `fuzz_codec` (C) and `diff_codec` (Rust, with C linked in) fuzz it directly, with Argon2id swapped for BLAKE2b in fuzzing builds only. `diff_codec` also checks C and Rust agree on hostile carriers and decode each other's output.

- No target fuzzes the **decode logic** (`decode_keyed`, `read_payload_v3`, `read_payload`, `open_box` sizing) on hostile images, because Argon2id is in the way. A target with a fixed or injected key would cover the length and size handling cheaply.
- No **cross-implementation codec fuzzing**: the `diff_*` targets compare loaders and save round-trips, and `tests/vectors.rs` and the CLI tests cover fixed cases. Nothing fuzzes "C encodes random cover and message → Rust decodes" or the reverse.
- No fuzzer or test checks **time or memory per input**. Finding 3 would pass under libFuzzer's default timeout.

## Checked and found sound

- **PNG parsing (C):** dimension and size overflow checks are done before allocating; the row-size check comes after the transforms; the setjmp handling is correct (`volatile img`, nothing modified after `setjmp` that the handler uses); the libpng allocator caps per allocation and in total; `read_end` saves and restores the jump buffer correctly.
- **JPEG (C and Rust):** the error handlers never return (longjmp in C, `C-unwind` with a caught payload in Rust); the area is checked before `jpeg_read_coefficients`; `max_memory_to_use` is honored by libjpeg-turbo's jmemnobs; coefficients are range-checked; embedding keeps every carrier at |v| ≥ 2 and within ±1023, and swaps never cross the empty -1..1 buckets.
- **Crypto:** a single Argon2id run (moderate) gives both subkeys through `crypto_kdf`; the salt is random per image; the 24-byte nonce is random; the MAC is checked before any plaintext is used; the length header can only be read with the scatter key, so for v2–v4 images no guess can be rejected before Argon2id. The v1 weakness is documented and only matters for v1 images; nothing can force the v1 path to decode a newer image.
- **Bounds:** `stc_carriers`, `block_start`, chunked Viterbi (embed and extract agree on chunk resets), `prng_sample` vs `prng_permutation` prefix equivalence, rejection sampling, `open_box` length underflow (always ≥ 40), `read_message` limits, and the `pt_len + 1` newline slot.
- **atomic_write:** `mkstemp` gives a 0600 temp file in the target's directory; mode and group are kept; FIFOs and devices are refused; flush, `fsync` and `close` errors are caught; the temp file is removed on failure. (Not covered: the directory isn't `fsync`ed after `rename`, and Ctrl+C during the write leaves the temp file behind. Neither is a security issue.) **Both fixed (2026-10-29)** in `c832d8c`.
- **Terminal and signals:** echo is restored on SIGINT, SIGTERM, SIGHUP and SIGQUIT; ignored signals stay ignored.
- **Verification run:** `make test` passed. That's unit tests and 94 CLI tests under `-fsanitize=address,undefined`, plus the fault-injection sweep, with no ASan, UBSan or LeakSanitizer reports.
