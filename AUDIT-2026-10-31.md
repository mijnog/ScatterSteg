Scope: the code changed between the last review (`34a31c3`, 2026-10-29; see [`AUDIT-2026-10-24.md`](AUDIT-2026-10-24.md)) and `75566c5`. That is 51 files, +4,581/−1,427 lines, chiefly:

- the message compressed before encryption, and inflated on extract;

- the WOW, S-UNIWARD and J-UNIWARD cost models (benchmark builds only).

Each claim in `THREAT_MODEL.md` that this code touches was treated as something to try to break, in both builds. Every finding below was reproduced with the C build at `75566c5`, and the Rust build was checked for the same behaviour. No code was changed.

**Bottom line.** No memory-safety bug, crypto misuse or cheaper passphrase test was found in the new code. The new parsers bound their work, and the inflate step refuses decompression bombs and trailing data. The passphrase reader keeps echo off and the bytes in locked memory on every path. One finding breaks a stated claim: the C build's PNG loader now holds the whole input file in memory, so a large hostile file costs unbounded memory (A5). ## Findings

### 1. Medium: C's PNG loader copies the whole input file into memory, with no limit (A5)

Since `b31f34b`, `png_read` reads through `tee_read`, which keeps a copy of every byte libpng reads, so that `png_write` can study the cover's compressed data. Nothing bounds it. libpng reads and discards what it doesn't keep (chunks past its 1000-chunk cache, extra IDAT data), and the tee keeps all of that too. The copy is made on every load, so `extract` and `info` pay for it on an untrusted image, though only `embed` uses it.

- **Reproduced:** a 64×64 RGB PNG followed by 1001 one-byte private chunks, then 48 private chunks of 8 MiB (403 MB in all). `scattersteg info` peaks at 395 MiB in C. Memory grows with the file (doubling `realloc`), so a 10 GB file needs more than 10 GB of memory.
- **Rust** reads files whole but refuses one over 1 GiB + 64 MiB (`rust/README.md`), so its cost is bounded. It is 388 MiB on the same file.
- **Claim broken:** A5, "no input file causes … unbounded memory use". Before `b31f34b` the C build streamed the file.
- **Fix:** keep the copy only when the image is loaded as a cover, and stop copying (mark it lost) past a cap. Or refuse files over Rust's cap, which also keeps the two builds' behaviour the same.

### 2. Low–Medium: a sender can choose a dotfile name, and `-f` lets it replace an existing file

`name_ok` admits any bare name but `.` and `..`. `extract` without `-xf` writes the message under that name in the current directory. A sender who knows the passphrase can therefore name it `.bash_login`, `.profile`, `.npmrc` or `Makefile`. Extracted in a home or project directory, that file runs or takes effect later. On a system that ships only `.profile`, a new `.bash_login` takes precedence at the next login shell.

- **Reproduced:** a message embedded from `.bash_login`. Plain `extract` refuses, because the user's `.bash_login` exists. `extract -f` replaces it with the sender's contents. In a directory without one, it is created with no warning.
- **Why `-f` matters:** `-f` is the user's way to say "replace the file I named", but here it also replaces a file the *sender* named. A user who types `-f` out of habit, to re-extract for instance, gives the sender write access to any file in the current directory.
- **Threat:** the sender knows the passphrase, so they are usually trusted. But a group passphrase, a compromised sender, or an image passed on by someone else all make this realistic, and steghide's behaviour is no reason to keep it.
- **Fix:** refuse a stored name beginning with `.` (embed would then need `-N` or a rename), or save it under a safe name and say so. Don't let `-f` replace a file whose name came from the image: only `-xf <name> -f` should.

### 3. Low: extracted plaintext is created readable by other users (A6)

`atomic_write` creates a new file with `0666 & ~umask`, so typically 0644. `mkstemp`'s 0600 is replaced before the message is written, so the temporary file is readable too. For the stego image that is right, since it is meant to be sent. For the decrypted message on a shared machine, any local user can read it until it is moved or deleted.

- **Reproduced:** with umask 022, the extracted file is 0644. Rust's `atomic_write.rs` does the same.
- **Fix:** have `extract` create its output 0600, keeping today's rule (the old file's mode and group) when it replaces a file. Leave `embed`'s output as it is.

### 4. Low: a stored name can carry terminal controls and bidi overrides

`name_ok` refuses bytes under 0x20 and 0x7F, but not UTF-8 encoded C1 controls (U+0080–U+009F, among them U+009B, CSI) or bidirectional overrides (U+202E). `extract` prints the name in "Wrote '…'" (and in `-v`'s "stored as '…'"). Some terminals act on C1 controls, and a bidi override can make the printed name read differently from the file created (`gpj.exe` displayed as `exe.jpg`). The code comment says such names can be printed "safely".

- **Reproduced:** a message stored from a file named `a<U+009B>31mb` is extracted under that name, and the bytes reach stderr raw.
- **Fix:** refuse names that aren't valid UTF-8 or that contain C1 controls, bidi controls (U+200E–U+200F, U+202A–U+202E, U+2066–U+2069) or other format characters. Alternatively, escape them when printing.

### 5. Low: the decoded file name is held in ordinary memory

The name is part of the plaintext, and `CONTRIBUTING.md` says plaintext stays in libsodium memory. C copies it into a stack array (`char name[CODEC_NAME_MAX + 1]` in `do_extract`), Rust into a `Vec<u8>` (`compress::unpack`). A name can be as revealing as the message (`meeting-tuesday-0300.txt`). The same applies on `embed` to the name taken from `-ef`, which comes from `argv` and so isn't secret from the process list anyway.

- **Fix:** keep the decoded name in `sodium_malloc` memory (C) or `Secret` (Rust), and wipe the stack copy. Alternatively, document the name as less protected than the message.

### 6. Low: the content-credential check misses remote manifests and maker-note signatures (A1)

`c2pa_manifest` looks for an APP11 JUMBF box labelled `c2pa`, which is how an embedded manifest is stored. It doesn't cover two other cases:

- **Remote manifests.** A C2PA manifest can be stored outside the file, referenced from XMP (`dcterms:provenance`). It still binds a hash of the image, so a checker that fetches it sees the changes as tampering.
- **Maker-note signatures.** Some cameras sign the image data in their maker notes: Canon's Original Decision Data, Nikon's Image Authentication. Their vendors' verifiers would also flag the output.

Both are uncommon, and neither shows a message is *present* rather than that the file was edited. But the C2PA refusal exists precisely because "edited" is enough to draw attention.

- **Fix:** refuse an XMP packet with a `provenance` reference, and say in `THREAT_MODEL.md` that maker-note signatures aren't detected. Recognizing the Canon and Nikon tags is possible, but it's more work for rare files.

### 7. Informational: the Huffman table rewrite relies on libjpeg's checks at load

`new_tables_into` indexes `fresh[8]` with the table's class and slot from the cover's DHT, and copies each table by the length its counts give, without checking either against the array or the segment. `dht_tables` does check. The code is only safe because libjpeg refuses, at load, a DHT whose class or slot is out of range or whose tables overrun the segment. Without those checks, a slot past 7 would read outside `fresh` and an overrun would copy past the header.

- **Fix:** repeat the two checks in `new_tables_into` (and in Rust's equivalent). If they fail, fall back to libjpeg's tables.

### 8. Informational: libpng's warnings reach stderr in C only

`png_read` leaves libpng's default warning handler in place, so C prints lines such as `libpng warning: prVt: no space in chunk cache`, where Rust prints nothing. `CLAUDE.md` asks for identical behaviour, wording included. Such warnings also tell anyone reading stderr what libpng was parsing.

- **Fix:** install a silent warning handler, as the JPEG loader does.

## Checked and found sound

- **Inflate (`unpack_message`, `compress::unpack`).** Two passes, the first only measuring. The output is capped at `RECORD_MAX`, the stream must end exactly at the input's end, and every buffer is in locked memory. A malformed record fails with an explicit message.
- **Name rules.** `/`, NUL and controls under 0x20 are refused on embed and extract in both builds, so no path traversal. An existing name, dangling links included, is refused without `-f`. Replacing goes through a temporary file and `rename`, and `atomic_write` refuses to replace anything but a regular file.
- **The passphrase reader.** Echo is restored on every exit path: errors, SIGINT, SIGQUIT, SIGTERM, SIGHUP, and Ctrl+Z (it stops, then asks again on resume). Signals that were already ignored stay ignored. Bytes go one `read()` at a time into `sodium_malloc` memory, overlong input is read to the newline without being stored, and a NUL is refused.
- **Message input.** `read()` into locked memory, growing by copy-and-wipe, bounded at the message cap plus one byte.
- **The length syndrome.** A wrong passphrase reads at most 2,048 samples for the length. The payload's allocation is then bounded by the image, as before (A5's peak-memory note still holds).
- **The trellis.** It refuses to walk back from an unreachable state (the `0b86d43` crash). UERD's flat-block cost is a finite 1e13, and HILL adds 1e-10 before its reciprocal, so a perfectly flat region has finite costs.
- **The PNG writer's layout search.** It runs on `embed` only. It is bounded: 41 zlib configurations over at most 8 MiB of image data, one filter byte per row, and inflation that stops once the rows are complete.
- **JPEG header copying.** The kept header is at most 16 MiB and must parse as whole segments ending at the first SOS, or it is dropped. The output is decoded and compared with the intended coefficients before it is used.
- **C2PA detection.** Both builds save APP11 segments whole (up to 64 KiB each, libjpeg's maximum) and search every one.
- **The command line.** Unknown options and missing values are refused, as are `-` for the cover or output. Commands check their options, `-xf -` writes unbuffered to stdout, and a directory or device as output is refused.
