# Notes for Claude

## The command line has steghide's syntax

ScatterSteg competes with steghide, so its command line uses steghide's commands and option names for every feature ScatterSteg has: a steghide user should only have to type `scattersteg` instead of `steghide`. The commands are `embed`, `extract`, `info`, `encinfo`, `version`, `license` and `help` (each also as `--embed` and so on); the options are `-ef`, `-cf`, `-sf`, `-xf`, `-z`, `-Z`, `-N`, `-f`, `-q`, `-v`, with steghide's long forms (`--embedfile`, ...).

- **Syntax only, never steghide's text.** Messages, prompts and help text are ScatterSteg's own wording. Don't copy or paraphrase steghide's.
- **New features:** if steghide has an option or command for the same thing, use its name and meaning. If not, pick a name that doesn't clash with one of steghide's. ScatterSteg's own extras so far: the `passphrase` command, `info`'s capacity and suggested-payload lines, and `embed`'s warning when a message is over the suggestion.
- **Deliberate differences, not bugs** (the README's "Coming from steghide" lists them for users):
  - `-p <passphrase>` is refused, with an explanation: the passphrase is always typed at the prompt, never on the command line where `ps` and shell history would show it. The owner decided this; don't add `-p`.
  - `-e` and `-K` are refused: the encryption is fixed (XSalsa20-Poly1305) and every message is authenticated.
  - `-cf -` and `-sf -` (cover from stdin, output to stdout) aren't supported.
  - An existing output file is refused unless `-f`; there is no yes/no prompt.
  - `info <image>` reports whether the image can be a cover, its capacity, and a suggested most to store (a byte per 160 pixels or non-zero AC coefficients, from the benchmarks' lightest payload). It doesn't look for a message: nothing can, without the passphrase.
  - Messages are always byte-exact (no newline added or removed).
- **Both front ends:** `main.c` (C) and `rust/src/main.rs` (Rust) must behave identically, wording included. `tests/test_cli.py` runs against each (`SCATTERSTEG=<binary>`).

## Detectability plan (2026-10-31)

The file format isn't frozen: nobody uses ScatterSteg yet, so a format change needs no compatibility path. Each step is measured before it's kept; every change lands in C and Rust together, with `FORMAT.md` and the tests. The README's "Status and plans" is the public version of this list.

0. **Done, merged:** `main` refuses JPEG covers carrying a content credential (C2PA), which the changes would visibly break. From the 2026-10-31 threat-model review, which also added pooled evidence, how files travel, unseen copies of the cover and device seizure (A7) to `THREAT_MODEL.md`.

1. **JPEG: embed in every AC coefficient** (zeros and ±1 included, UERD or J-UNIWARD costs, ±1 either way) instead of only |value| ≥ 2. UED, UERD and J-UNIWARD all do; nsF5-style skipping crowds the changes. **Merged 2026-10-31.** Prototype was branch `jpeg-all-coefs` (`b702512`; 8 test checks still expect the old rule). **DCTR result (2026-10-31, `~/bench/run-distortion/results-allcoef.txt`):** P_E old → all-coefficients, UERD 0.485/0.464/0.397/0.261 → 0.473/0.456/0.418/0.356 at 0.05/0.1/0.2/0.3; J-UNIWARD 0.496/0.468/0.382/0.232 → 0.470/0.462/0.425/0.360. A clear gain from 0.2 up, slightly worse at 0.05 (1–2 sd; maybe tune a small extra cost on zeros, as `JPEG_TWO_COST` was tuned). Histogram shifts (`hist_jpg.py`, on `jpeg-all-coefs`) all ≤ 0.1 cover sds, against up to 1.6 (UERD) and 3.2 (J-UNIWARD) for the old rule at 0.3; every cover now fits 0.3. **SRNet result:** `uerdall_0.2` (fine-tuned from `uerd_0.2`'s detector) has P_E 0.0777 on the 1,955 test images `uerd_0.2` kept, against 0.0734 (bootstrap sd 0.0039: no real difference); 0.0765 on all 2,000. The 45 smooth images the old rule couldn't fit are caught almost always (P_E 0.022). Owner's call: go ahead. **Done (merged):** C and Rust, tests updated, carriers implicit (one pointer per block; cap 14 bytes per carrier, ~50 MP for 4:2:0), `JPEG_TWO_COST` gone, docs and benchmark tables updated. Smooth covers: not the new rule's doing. At 0.2 bits per nonzero AC, SRNet's P_E by nonzero-AC share runs from 0.002 (smoothest tenth) to 0.176 (busiest quarter), the same under both rules (`benchmark/README.md`). So the "guard" belongs in step 4: the payload suggestion and embed's warning should scale with texture, calibrated on the new rule's light-payload runs (`train_queue4.sh`).
2. **Write files the way the cover was written** (audit finding 7): the output's structure identifies ScatterSteg, and the C and Rust builds, without any steganalysis. **PNG done, merged:** the cover's row filters, IDAT size and the zlib settings that reproduce its data (tried in a fixed order, same in C and Rust); C writes the file itself, Rust uses the system zlib, and `diff_png` checks the bytes match. 55 covers (Pillow, ImageMagick, zlib incl. Z_RLE) resave byte-identical; level-0 stored blocks can't always be matched. **JPEG done, merged:** a single-scan sequential Huffman JPEG keeps the cover's header bytes (kept at load) and Huffman tables; where the changed coefficients need a code they lack (libjpeg-turbo silently writes a 0-bit code, so every such output is decoded and checked), optimized tables go into the cover's DHT segments and slots; else libjpeg's way. 89 camera files (`ianare/exif-samples`): all usable ones keep their layout after embedding, 85 resave identical; C and Rust write the same bytes (219 covers; `diff_jpeg` now checks it, after changing coefficients too). Not done: progressive scan scripts other than libjpeg's (no test covers), fill bytes before EOI, padding-bit quirks.
3. **Ternary embedding** (multi-layer STC; the message picks +1 or −1): fewer changes per bit, as the published HILL/UERD/J-UNIWARD results assume.
